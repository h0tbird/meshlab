Refresh this list at any time with:

```bash

  exec istio-eastwestgateway-sidecar-istio-7c5fc4bb7f-bzxkw -- \
  pilot-agent request GET /stats/prometheus
```

> **Note on visibility.** This gateway currently emits only **TCP** Istio
> telemetry (`istio_tcp_*`) plus Envoy admin/cluster/listener stats. There are
> **no L7 metrics** (`istio_requests_total`, `istio_request_duration_milliseconds`,
> `istio_request_bytes`, …) because traffic through the east-west gateway is
> proxied at L4 (TLS passthrough / mTLS tunnel), so Envoy never parses HTTP.
> Envoy's own per-cluster/per-listener stats are also trimmed by Istio's default
> stat matcher. See [Gaining more visibility](#gaining-more-visibility) below.

## Gaining more visibility

If the current set is not enough, here are the main levers to expose more:

1. **Expose more of Envoy's built-in stats (per-listener/HTTP/TCP proxy stats).**
   Istio trims Envoy stats by default. Widen the matcher via the pod annotation
   or mesh-wide `ProxyConfig`:

   ```yaml
   # pod / gateway template annotation
   proxy.istio.io/config: |
     proxyStatsMatcher:
       inclusionRegexps:
       - ".*"                      # everything (noisy — scope in prod)
       inclusionPrefixes:
       - "listener"
       - "tcp"
       - "http"
   ```

   Useful prefixes for a TCP gateway: `tcp.*` (TCP proxy filter stats such as
   `downstream_cx_total`, `downstream_cx_rx_bytes_total`), `listener.*`
   (per-listener `downstream_cx_*`, SSL handshake stats), and `http.*` if any
   HTTP listeners exist.

2. **Add downstream (server-side) TCP telemetry.** The series above are all
   `reporter="source"`. Whether both source and destination reporters appear
   depends on where mTLS terminates; confirm with a `reporter="destination"`
   filter and, if missing, review the `Telemetry` API config for the gateway.

3. **Enable L7 metrics** (`istio_requests_total`,
   `istio_request_duration_milliseconds`, `istio_request_bytes`,
   `istio_response_bytes`). These only appear when the gateway processes HTTP.
   For an east-west gateway doing TLS passthrough / mTLS tunneling this is not
   applicable; L7 stats require an HTTP route through the gateway instead of raw
   SNI/TCP forwarding.

4. **Customize Istio dimensions with the Telemetry API.** Add/remove labels
   (tags) on the `istio_tcp_*` metrics via a `Telemetry` resource
   (`metrics.overrides.tagOverrides`) — e.g. to add `request_protocol` detail or
   drop high-cardinality labels.

5. **Raise Envoy admin verbosity temporarily** for ad-hoc debugging:

   ```bash
   kubectl --context kind-pasta-1 -n istio-system \
     exec istio-eastwestgateway-sidecar-istio-7c5fc4bb7f-bzxkw -- \
     pilot-agent request GET /stats                 # full raw Envoy stats (not Prometheus-formatted)
   ```

   `/stats` (without `/prometheus`) returns the complete, untrimmed Envoy stat
   tree and is handy for discovering which counters exist before deciding what to
   promote into the Prometheus scrape via `proxyStatsMatcher`.

## Diagnosing 503 UC

`503 UC` is an **HTTP response flag** — `UC` = *UpstreamConnectionTermination*
(the upstream dropped the connection while a request was in flight). It is
emitted by the **HTTP connection manager on the client-side proxy**, never by
this gateway: the east-west gateway is pure **L4 SNI passthrough**
(listener `0.0.0.0_15443` → `tls_inspector` + per-SNI `tcp_proxy` filter
chains, no `http_connection_manager`), so it forwards an already-mTLS-encrypted
byte stream and never produces a 503 or a `UC` flag. From the client's point of
view "upstream" is the tunnel that runs *through* this gateway, so you diagnose
it by asking **did the gateway fail to route, or tear down, the TCP tunnel?** —
not by looking for a `UC` counter here.

### How the gateway routes (why SNI matters)

Each filter chain matches a single SNI of the form
`outbound_.<port>_._.<service>.<namespace>.svc.pasta.local` and forwards to a
cluster of the same name. If the client presents an SNI that matches **no**
chain, or the matched cluster has **no healthy endpoints**, the gateway drops
the connection and the client records `503 UC`.

### Signals already exposed (no config change needed)

Filter these `envoy_cluster_*` series by the offending
`cluster_name="outbound_.<port>_._.<svc>.<ns>.svc.pasta.local"`:

| Metric | What it tells you about a UC |
|---|---|
| `envoy_cluster_upstream_cx_destroy_remote_with_active_rq` | The real backend reset the connection mid-request — the closest root-cause signal for UC. |
| `envoy_cluster_upstream_cx_destroy_remote` | Remote-initiated teardown (backend closed / restarted). |
| `envoy_cluster_upstream_cx_connect_fail` | Gateway could not connect upstream. |
| `envoy_cluster_upstream_cx_connect_timeout` | Upstream connect timed out. |
| `envoy_cluster_upstream_cx_none_healthy` | No healthy endpoint at connect time. |
| `envoy_cluster_membership_healthy` / `envoy_cluster_membership_total` | `healthy == 0` → every connection to that service fails. |
| `istio_tcp_*{response_flags!="-"}` | Group the Istio TCP series by `response_flags` to spot the gateway recording a flag for a specific peer. |

### Extra signals after enabling `listener` + `tcp` prefixes

Add `listener` and `tcp` to `proxyStatsMatcher.inclusionPrefixes` (see
[Gaining more visibility](#gaining-more-visibility)). Because each filter chain
uses its SNI as the `stat_prefix`, you then get **per-destination** counters:

| New stat | What it tells you about a UC |
|---|---|
| `listener.0.0.0.0_15443.no_filter_chain_match` | Client SNI matched no chain → gateway resets → client sees UC. **Top suspect for config/SNI drift.** |
| `tcp.<sni>.downstream_cx_no_route` | SNI matched a chain but its cluster has no route/endpoints. |
| `tcp.<sni>.idle_timeout` | Tunnel closed by idle timeout → next client request sees UC. |
| `tcp.<sni>.downstream_cx_total` / `downstream_cx_rx_bytes_total` | Confirms the tunnel is actually reaching the gateway for that destination. |
| `listener.0.0.0.0_15443.downstream_cx_destroy` / `downstream_pre_cx_timeout` | Early / pre-handshake connection teardowns. |

> **Note:** these chains *pass TLS through* (the gateway only sniffs SNI, it does
> not terminate app mTLS), so `ssl.*` handshake stats on this listener are not a
> useful signal here — TLS/cert failures surface on the **destination** sidecar
> or ztunnel instead.

### Recommended workflow

1. On the **client sidecar**, find the access-log line with `response_flags="UC"`;
   note the `upstream_host` / cluster and the SNI/authority.
2. On **this gateway**, check the matching `cluster_name` against the
   already-exposed `envoy_cluster_upstream_cx_destroy_remote_with_active_rq`,
   `upstream_cx_connect_fail`, and `membership_healthy`. If those are flat,
   enable `listener`/`tcp` and watch `no_filter_chain_match` and
   `tcp.<sni>.downstream_cx_no_route`.
3. On the **destination sidecar / ztunnel**, confirm whether the final hop reset
   (app crash/restart, keepalive vs. idle-timeout mismatch, or PeerAuthentication
   / mTLS failure).
4. Enable access logging on the gateway for correlation — metrics tell you *how
   often*; logs tell you *which connection* and *why*.
