## Diagnosis: why `sidecar → remote ambient` fails here

The lab is **not** misconfigured. Chain of evidence:

1. **Sidecar EDS asymmetry.** From a sidecar in `c1/s1`:
   - `outbound|80||peer.swarm-sidecar-n2` → local pod `10.51.0.28:8082` **and**
     remote gateway `172.18.0.18:15443` ✅
   - `outbound|80||peer.swarm-ambient-n2` → only
     `connect_originate/10.51.0.26:8082` (local pod). No remote entry at all.
2. **Scale-to-zero proof.** Scaling `c1 swarm-ambient-n2/peer` to 0 left the
   cluster with **zero** endpoints — despite a healthy `10.52.0.25` in `c2` and
   `istio.io/global: "true"`. The peers immediately logged
   `503 "no healthy upstream"`. Restored afterwards.
3. **Root cause** — `pilot/pkg/xds/endpoints/ep_filters.go` (1.30.3):
   ```go
   // Cross-network traffic relies on mTLS for SNI routing in sidecar mode.
   if (!features.EnableAmbientMultiNetwork || isSidecarProxy(b.proxy)) && !isMtlsEnabled(lbEp) {
       continue
   }
   ```
   `isMtlsEnabled` tests `security.istio.io/tlsMode=istio`, a label applied by
   **sidecar injection**. Verified on the live pods:
   | pod | tlsMode |
   |---|---|
   | `swarm-ambient-n2/peer` (c1 and c2) | `<none>` |
   | `swarm-sidecar-n2/peer` (c1 and c2) | `istio` |

   Ambient pods can never satisfy it, so for a sidecar proxy every remote
   ambient endpoint is dropped before gateway selection runs.
4. **Corroborating filter** — `selectNetworkGateways()` in the same file:
   `// Sidecar proxies cannot talk to ambient E/W gateway for now`, dropping
   any gateway with `Port == 0` (the HBONE-only ambient gateway).

So there is no configuration that fixes this on 1.30.3; it is hard-coded.

### Why the reporter may believe it works

- **Most likely: local endpoints masked it.** In multi-primary the same service
  usually exists in both clusters, so requests are silently served locally and
  the cross-cluster path is never exercised. Their own observation #3 (503 UH
  when a backend resolves only remotely) is arguably the same bug surfacing
  once there is no local endpoint left to mask it.
- **Their "ambient" namespace may still be injecting sidecars.** If so the pods
  carry `tlsMode=istio` and the filter passes — but they aren't ambient.
- Testing from an ingress/waypoint rather than an actual sidecar.

### Relevant feature-flag defaults in 1.30.3 (`pilot/pkg/features/ambient.go`)

| Flag | Default |
|---|---|
| `AMBIENT_ENABLE_MULTI_NETWORK` | `false` |
| `AMBIENT_ENABLE_MULTI_NETWORK_WAYPOINT` | `true` (no-op unless the above is true) |
| `AMBIENT_ENABLE_MULTI_NETWORK_INGRESS` | `false` |

This is a plausible answer to their #3: with `AMBIENT_ENABLE_MULTI_NETWORK`
unset, `ep_filters.go` makes waypoints skip remote-network endpoints entirely,
yielding a programmed route with an empty cluster → `503 UH`.

I have a reproducible two-cluster lab with exactly this topology, so here is some empirical data that may help answer 1–3. Note I'm on **1.30.3**, not 1.27.3, so this shows where things stand several releases on.

## Setup

- **Istio**: istiod built from tag `1.30.3` (commit `56df41f63e`), ztunnel + proxies `1.30.3`
- **Topology**: 2 primary clusters, multi-network — distinct network IDs `pasta-1` / `pasta-2`, distinct pod CIDRs
- **Both E/W gateways present**, as in your setup:
  - `istio-eastwestgateway-ambient` — `gatewayClassName: istio-east-west`, HBONE `:15008`
  - `istio-eastwestgateway-sidecar` — `gatewayClassName: istio`, TLS passthrough `:15443` (AUTO_PASSTHROUGH)
- `AMBIENT_ENABLE_MULTI_NETWORK=true`, `PILOT_ENABLE_ALPHA_GATEWAY_API=true`
- Services labelled `istio.io/global: "true"`; remote secrets in place
- 4 namespaces per cluster, each running the same HTTP peer workload that calls every other peer continuously

One deliberate difference from your setup worth calling out up front: in my lab the pod CIDRs **are** routable between clusters at L3. The clusters are only split into two Istio networks by the `network` label, which is what forces traffic through the E/W gateways. I mention this because it isolates the variable — nothing below is caused by missing L3 reachability. The same lab with the network labels collapsed (and no other change) behaves completely differently; I'll post that as a follow-up.

## On your three questions

**2. ambient → remote sidecar: confirmed still failing on 1.30.3.** Matches your observation. ztunnel sends (double-)HBONE to the ambient E/W gateway, which forwards HBONE onward — but a sidecar pod has no ztunnel and no HBONE listener, and the ambient E/W gateway has no logic to downgrade HBONE to plain mTLS toward a sidecar. Tracked upstream as istio/istio#57877.

**1. sidecar → remote ambient: I get ❌, and I think it's worth re-checking your "works".** I dug into this specifically because your report disagreed with my matrix.

From a sidecar in `c1/s1`, the EDS asymmetry is stark:

```
# remote SIDECAR service - has the remote E/W gateway
outbound|80||peer.swarm-sidecar-n2.svc.pasta.local
  10.51.0.28:8082        HEALTHY   <- local pod
  172.18.0.18:15443      HEALTHY   <- remote cluster via sidecar E/W gw

# remote AMBIENT service - local pod only, no remote entry whatsoever
outbound|80||peer.swarm-ambient-n2.svc.pasta.local
  envoy://connect_originate/10.51.0.26:8082   HEALTHY   <- local pod
```

So the cross-cluster plumbing itself is fine — it's specifically the ambient destination that never gets a remote endpoint. To rule out "it's there but deprioritised", I scaled the **local** `swarm-ambient-n2` backend in `c1` to zero. The cluster went completely empty, even though `c2` had a healthy pod and the service carries `istio.io/global: "true"`:

```
=== sidecar EDS for peer.swarm-ambient-n2 AFTER removing local endpoint ===
ENDPOINT     STATUS     OUTLIER CHECK     CLUSTER
(empty)
```

...and the client immediately started logging **exactly your #3 symptom**:

```json
{"service": "peer.swarm-ambient-n2:80", "http": {"status":503}, "body": "no healthy upstream"}
```

The cause is in `pilot/pkg/xds/endpoints/ep_filters.go`:

```go
// Cross-network traffic relies on mTLS for SNI routing in sidecar mode.
// TODO BTS may allow us to work around this
if (!features.EnableAmbientMultiNetwork || isSidecarProxy(b.proxy)) && !isMtlsEnabled(lbEp) {
    continue
}
```

For a sidecar proxy this reduces to "drop every remote endpoint that isn't mTLS-enabled". `isMtlsEnabled` tests the `security.istio.io/tlsMode=istio` label, which is applied by **sidecar injection** — so an ambient pod can never satisfy it. Confirmed on my pods: ambient peers have no `tlsMode` label, sidecar peers have `tlsMode=istio`. The same file also states plainly, in `selectNetworkGateways()`:

```go
// Sidecar proxies cannot talk to ambient E/W gateway for now, so when we see an ambient
// E/W gateway (e.g., a gateway that listens on hbone port, but does not have an mTLS port
// we filter it out.
```

Tracked as istio/istio#57878.

**So if it works for you, I'd love to know what's different** — but two things are worth ruling out first:

1. **Local endpoints masking the test.** In multi-primary the same service usually exists in *both* clusters, so a sidecar can appear to succeed while every request is served by the local endpoint and the cross-cluster path is never exercised. Scaling the local backend to 0 (as above) is the cleanest way to check.
2. **Whether the destination is genuinely ambient.** If the "ambient" namespace still has sidecar injection enabled, the pods carry `tlsMode=istio`, the filter passes, and it will work — but via the sidecar path, not ambient.

Worth noting your #1 and #3 observations are in tension with each other: #3 is what this code produces when there's no local endpoint to fall back on.


**3. waypoint → remote global-service backend.** I can't reproduce your exact setup (my waypoints resolve service endpoints rather than an explicit `VirtualService` backend), but one thing worth checking is `AMBIENT_ENABLE_MULTI_NETWORK`. On 1.30.3 it still defaults to **false**, and in `ep_filters.go` a waypoint will `continue` past every remote-network endpoint unless it is enabled:

```go
if !b.proxy.InNetwork(epNetwork) && features.EnableAmbientMultiNetwork {
    if !features.EnableAmbientWaypointMultiNetwork && model.IsWaypointProxy(b.proxy) ||
        !features.EnableAmbientIngressMultiNetwork && model.IsIngressGateway(b.proxy) {
        continue
    }
    ...
```

That produces precisely what you describe: a correctly programmed route whose cluster has no endpoints → `503 UH`. Related flags on 1.30.3: `AMBIENT_ENABLE_MULTI_NETWORK_WAYPOINT` defaults true (but is a no-op unless `AMBIENT_ENABLE_MULTI_NETWORK` is true), and `AMBIENT_ENABLE_MULTI_NETWORK_INGRESS` defaults **false**, so ingress gateways keep traffic local by default. Flag names may differ on 1.27.3.

With `AMBIENT_ENABLE_MULTI_NETWORK=true` set, my source ztunnel reports `2/2` endpoints and the waypoint EDS carries pod IPs from both clusters, so waypoint-fronted cross-cluster resolution does populate on 1.30.3.

⚠️ **One methodology trap worth flagging**, since it invalidated my own first run: ztunnel load balances **per TCP connection**, not per request. Any client reusing an HTTP keep-alive connection gets pinned to whichever endpoint the first connection landed on, permanently — so an ambient client can look like it only ever reaches one cluster. I had to disable HTTP keep-alives in the test workload before these numbers became meaningful. Sidecars aren't affected, because Envoy re-balances per request.

## Summary

For 1.30.3, multi-network: **cross-cluster only works when both ends are the same data-plane mode.** Aligning both ends of each cross-cluster call to the same mode is, as you guessed, the workable path today.

I'll follow up with single-network results, which look very different.

## Setup delta

Identical to the previous comment — same Istio 1.30.3 build, same workloads, same 8 namespaces, same routable pod CIDRs. **The only change is the Istio `network` label**: both clusters now report the same network, so istiod treats them as one.

Take the gateway out of the path and the mode mismatch simply stops mattering.

## Two gotchas worth documenting

1. **`AMBIENT_ENABLE_MULTI_NETWORK=true` is still required**, even though there is only one network. The flag name is misleading: it is effectively the master switch for ambient *cross-cluster* endpoint discovery, independent of network topology. With it `false` in single-network mode I saw `istioctl ztunnel-config service` report `1/1 ENDPOINTS` for a service with pods in both clusters, and zero remote workloads in `ztunnel-config workload` — while sidecar Envoy EDS saw everything. So the gap was purely on the ambient path.

2. **ztunnel applies no locality preference by default.** `constructService` in `pilot/pkg/serviceregistry/ambient/services.go` only emits a `workloadapi.LoadBalancing` when the Service sets `internalTrafficPolicy: Local` or a `trafficDistribution` value; otherwise it's `nil` and selection is uniformly random across all endpoints, local and remote alike. `DestinationRule` `localityLbSetting` / `failoverPriority` are ignored by ztunnel (they are honored at the waypoint). Combined with per-connection load balancing, this is what makes the keep-alive pinning effect I mentioned earlier so easy to misread.

If it's useful, an explicit support matrix in the docs distinguishing single-network from multi-network for mixed sidecar/ambient would have saved me a lot of time — the two behave completely differently for cross-mode cross-cluster.
